# GetScouted Backend

## What This Is

A Django/DRF backend for GetScouted, an AI-powered football recruitment and scouting platform (built for World In Motion Ltd) used by agents, recruitment analysts, and club decision-makers. This backend replaces the Supabase layer currently behind the `pixel-perfect-clone-60729` frontend prototype, serving real player/club/transfer data and computing the platform's core scores for real — including natural-language search and AI-generated scouting insights.

## Core Value

The backend must serve accurate, real scouting data and real (not approximated) Impact RMM scoring — the product's credibility rests on the scores being right, not just on the API being reachable.

## Requirements

- ✓ Auth with roles (scout, analyst, director, admin) — Phase 2: custom Django `accounts.User` (UUID PK, email login) is now `AUTH_USER_MODEL`, replacing Supabase Auth and the other 2 legacy auth models; DRF+simplejwt wired deny-by-default; registration/login/refresh/logout/password-reset endpoints live; reusable `MinimumRole` role-hierarchy permission primitive built and proven via `/api/auth/me/` and `/api/auth/admin/users/`, ready for Phase 7/8 reuse on Watchlist/Shortlist/SquadPlan
- ✓ Live scoring API for all 4 core scores (RMM, CS, TFM, Transfer Probability) — Phase 4: 5 authenticated endpoints under `/api/scoring/` (4 per-score + 1 combined Player Profile summary), each returning a real computed value with a full component breakdown (SCORE-01 through SCORE-05), wrapping Phase 3's faithfully-characterized calculators as a Django service layer. Verified via real execution against the live 41,708-player dev DB, not just static review. Two real risks caught before shipping: an sklearn model output that would have returned log-scale numbers (€ millions reported as ~13-17) instead of real money, and a compatibility-score breakdown that would have silently disagreed with the score it was explaining. Deliberately out of scope for this phase (by roadmap design): O(1) caching (Phase 6) and numerical parity testing against Phase 3's oracle (Phase 5) — endpoints are correct but not yet fast.
- ✓ Scoring parity proven — Phase 5 (SCORE-06): an automated pytest parity suite (`scoring/tests/test_parity_{bulk,api_sample,edge_cases}.py`) proves the Django port's RMM/CS/TFM/Transfer Probability match Phase 3's oracle snapshot, parametrized across all 10 real position groups (not the 8 originally assumed — corrected during research), plus a seeded per-request/DRF-endpoint sample and 7 dynamically-mined real-data edge cases (zero-minutes, missing stats, boundary ages, invalid position). Verified against the real 41,708-player dev DB. Caught and fixed a real bug during planning (not execution): a `player_id` UUID-vs-string index mismatch that would have made the bulk suite silently all-fail and the API-sample suite crash, regardless of whether the underlying scores were correct.

- ✓ Live scoring is fast — Phase 6 (SCORE-07): the 5 live `/api/scoring/` endpoints from Phase 4 now read from a denormalized `Player` field or an in-process memoized aggregate for the common "player vs their own club" case, instead of recomputing the full 41,708-player population on every request. Real measured improvement against the live dev DB: RMM 9.15s→0.06s, Compatibility 44.2s→0.16s, Financial Fit→0.004s, combined Summary→0.20s. The initial phase-goal verification correctly caught that the caching infrastructure (built first) hadn't actually been wired into the live API yet — a gap-closure pass fixed that before the phase was marked done. Arbitrary-other-club scoring (e.g. "rank this player against every club") intentionally still computes live, deferred to Phase 12.
- ✓ Browse/filter/inspect API for Players & Clubs — Phase 7 (CRUD-01 through CRUD-05): `/api/players/` and `/api/clubs/` support filter/sort/pagination (position, age, market value, league, score thresholds, playing style), single-entity detail (Player detail composes full profile + score breakdowns via the now-fast `get_summary()`; Club detail composes squad + transfer aggregates), and an `?ids=` multi-fetch for side-by-side comparison, reusing the same list endpoints rather than bespoke routes. Verified against the real 41,708-player/1,060-club dev DB. Caught and fixed a real cross-phase regression before completion: a project-wide pagination default silently broke Phase 2's `/api/auth/admin/users/` endpoint, which expected a plain list — fixed by scoping pagination to the new list views explicitly instead of a global default.
- ✓ Personal scouting workspace API — Phase 8 (CRUD-06 through CRUD-10): new single `workspace` app delivers Watchlist (per-`(user,player)` row, duplicate-safe), club-scoped Shortlists with player entries/notes, Squad Plans (formation + `proposed_changes` delta, `current_squad` always derived live — never frozen, so Phase 11's simulation work has a stable contract to compute against), auto-logged Recent Activity (Phase 7's `PlayerDetailView`/`ClubDetailView` write a row on every authenticated GET — no separate manual-log endpoint), and CSV export for both a Shortlist and a Club report via stdlib `csv` + `StreamingHttpResponse` (no new dependency). Ownership enforced by a new object-level `IsOwner` permission; every list/create surface additionally scopes `get_queryset()` by `request.user` since DRF's object-level permission alone never fires on list/create — the single highest-risk mistake this phase's research flagged, mitigated on every one of the 4 viewsets and live-verified (cross-user access correctly 404s). Verified against the real dev DB and live HTTP requests, not just plan self-reports; zero regressions to Phase 7's detail-view tests.
- ✓ Natural-language player search, provider-agnostic — Phase 9 (AI-01, AI-02, AI-05): `POST /api/players/search/` translates plain-English queries (e.g. "young left-backs under €5M at possession-based clubs") into real, structured filters via Anthropic's Messages API (forced tool-use, output constrained to the fixed field whitelist — position/league/age/market-value/score fields, plus "style" resolved through the player's club since `Player` itself has no style field). `AI-05`'s provider-agnostic claim is real, not aspirational: calling code only ever imports the abstract `NLQueryParser` interface via a `get_nl_query_parser()` factory, never the concrete Anthropic class directly (grep-verified). Never an error or empty result — a 3-tier degradation (LLM parse → deterministic keyword/regex fallback → unfiltered list) always returns HTTP 200, live-verified end-to-end with no API key configured at all. Every search call logs to `RecentActivity` as `"searched"`, completing the contract Phase 8 deliberately left unpopulated. Caught a real silent-failure risk during research: `PlayerFilter` ignores unrecognized `club__`-prefixed keys instead of erroring, which would have silently shipped unfiltered "style" results — fixed with a separate manual filter step, live-verified against the real dev DB (41,708 → 14,252 with the fix applied; unchanged at 41,708 without it).
- ✓ AI-grounded scouting reports and club insights — Phase 10 (AI-03, AI-04): `POST /api/players/{id}/scouting-report/` and `POST /api/clubs/{id}/insights/` generate narrative text via a new `ReportGenerator` interface (mirroring Phase 9's `NLQueryParser` pattern exactly), but every number in that narrative is enforced, not just prompted-for — a post-generation grounding validator extracts every numeric token from the LLM's output and rejects (retries once, then fails clean) any number that doesn't trace back to the pre-computed grounding dict (`get_summary()` for player reports, a bounded single-club ORM position-needs aggregation + `ClubDetailSerializer`'s transfer aggregates for club insights). On any failure (LLM error or grounding validation failing twice), the endpoint returns a clean error — never a fabricated report, verified by a dedicated test asserting no narrative content leaks into the error body. Resolved a real cross-phase gap during discussion: Phase 10 needed "Position Needs" data but the canonical Position Needs feature is Phase 11 (which comes after and wasn't even a dependency) — solved by computing a narrow, internal-only aggregation scoped to this phase's actual need, not building Phase 11's feature early. Research also caught that the Anthropic-call-blocking pytest safety net only existed in `players/tests/`, not `clubs/tests/` — ported before any club-insights test could accidentally fire a real billed call. Full suite: 214 passed, 0 failed, independently re-verified. Live real-LLM narrative-quality spot-check honestly deferred (no API key available in this environment), documented as a manual follow-up rather than faked.
- ✓ Position Needs analysis and squad-change simulation — Phase 11 (PLAN-01, PLAN-03): `GET /api/clubs/{id}/position-needs/` extends Phase 10's internal aggregation with a concrete weak/at-risk/strong classification per position (weak: depth<2; at-risk: adequate depth but avg age>30 or half+ contracts expiring within 12mo; strong otherwise). `POST /api/workspace/squad-plans/{id}/simulate/` applies add/remove/swap changes to the live squad entirely in memory — live-verified the database is genuinely unchanged after every call — and reuses Phase 8's existing SquadPlan update endpoint as the "commit" step rather than building a redundant new one. Avoided a real correctness trap: squad-average metrics use `impact_score` (confirmed club-independent) rather than `compatibility_score`/`financial_fit_score`/`transfer_probability_score` (own-club-context fields that would silently be wrong for an incoming player from a different club); null `market_value`/`age`/`impact_score` values are excluded from averages, never coerced to 0. Both plans ran in the same wave, fully parallel (disjoint `clubs`/`workspace` apps), with zero conflicts. Full suite: 231 passed, 0 failed, independently re-verified.

## Context

- **Existing codebase** (`/Users/MAC/Desktop/getScouted/`) has 3 separate sub-projects, each its own git repo:
  - `API-Updated-/` — legacy Node/Express + MongoDB REST API (JWT auth; API-key middleware currently disabled). Real CSV datasets live under `API-Updated-/dataset/` (Players, Playstyles, per-position stats with leagues, Compatibility Scores, transfer history).
  - `RT-Tool-Frontend/` — legacy React/Vite client of `API-Updated-`. Not the target frontend for this backend.
  - `pixel-perfect-clone-60729/` — newer Lovable-generated React/TanStack Start prototype implementing the PRD's 6-page vision, currently backed by Supabase (see `supabase/migrations/`). Contains `docs/impact_model_v4.1.py`, a ~15,700-line pandas-based scoring engine ("Impact RMM 4.1") that is currently **unused in production** — the frontend instead approximates scoring with a crude client-side heuristic in `src/lib/domain.ts`.
- `GetScouted PRD.docx` (Jan 2026, World In Motion Ltd) defines the 6-page platform and 4 core scores: Player Score (RMM), Compatibility Score (CS), Financial Fit (TFM), Transfer Probability, plus AI-generated insights/search/scout reports.
- A full codebase map exists at `.planning/codebase/` (STACK, ARCHITECTURE, STRUCTURE, CONVENTIONS, TESTING, INTEGRATIONS, CONCERNS) covering all 3 sub-projects.
- **Known risks surfaced during mapping** (see `.planning/codebase/CONCERNS.md`):
  - 3 conflicting auth models across the legacy pieces (JWT, disabled API-key middleware, Supabase Auth) need reconciling into one Django approach
  - Field-naming mismatches across MongoDB / CSVs / Supabase / the Python scoring model — though the Python model already uses consistent snake_case, which aligns naturally with Django/Postgres conventions
  - Zero test coverage anywhere in the existing codebase, most notably on the ~15,700-line untested scoring logic that now needs porting
- Existing Supabase migrations show a workable reference schema (clubs, players with jsonb attributes, profiles, user_roles enum, watchlist, squad_plans, recent_activity) — useful as a reference, not a mandate, for the new Django schema.

## Constraints

- **Tech stack**: Django + Django REST Framework, Postgres — replaces both MongoDB (legacy) and Supabase (prototype)
- **Timeline**: 4-day demo/deadline target — treated as a *soft* target. The user explicitly chose to keep full scope rather than cut it to fit 4 days; progress will be reported realistically against the deadline instead of force-fitting scope.
- **Scope boundary**: backend-only — no frontend rewiring of `pixel-perfect-clone-60729` in this project
- **LLM integration**: built behind a provider-agnostic interface (`NLQueryParser`) — Phase 9 picked Anthropic Claude as the first concrete implementation, swappable via `LLM_PROVIDER` env var with zero calling-code changes
- **Hosting**: undecided; backend should be Docker/12-factor-friendly so this doesn't block development
