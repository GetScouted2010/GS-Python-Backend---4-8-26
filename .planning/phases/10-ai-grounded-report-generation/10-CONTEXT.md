# Phase 10: AI Grounded Report Generation - Context

**Gathered:** 2026-07-25
**Status:** Ready for planning

<domain>
## Phase Boundary

Authenticated users can request an AI-written scouting report for a player (strengths, weaknesses, tactical fit, financial fit, best use case) and AI-generated club insights (recruitment gaps, over-aged positions, financial constraints). Both are narrative text generated by an LLM, but every single number that appears in that narrative must trace back to an already-computed score, stat, or aggregate — the LLM writes prose around real numbers, it never invents or estimates one. This phase does NOT compute new scores (that stays 100% deterministic, per this project's core value), does NOT build the full canonical Position Needs analysis endpoint (that's Phase 11's PLAN-01 — this phase only needs internal grounding data for club insights, not a user-facing "view your Position Needs" feature), and does NOT build squad simulation (Phase 11's PLAN-03).

All decisions below were made by Claude on the user's standing instruction ("make all necessary and important decisions considering trade-offs and execute") rather than through interactive discussion. Rationale is spelled out for each so downstream agents (and the user, on review) can see why.

</domain>

<decisions>
## Implementation Decisions

### Cross-phase gap: Phase 10 needs "Position Needs" data, but Phase 11 builds that feature
- **Decision:** Phase 10 computes its own lightweight, internal-only position-needs aggregation (squad depth per position, average age per position, count of contracts expiring within 12 months per position) directly from real `Player` data (`position`, `age`, `contract_expires`, `club` — all confirmed to exist) — used purely as grounding input for the club-insights LLM prompt. This is NOT the same as Phase 11's `PLAN-01` "Position Needs analysis (strong/weak/at-risk)" — no public endpoint, no strong/weak/at-risk classification labels, no user-facing "view your Position Needs" feature. Phase 11, built later, may reuse or formalize this aggregation logic into its own dedicated feature; Phase 10's version is deliberately narrower (just the numbers a report needs, not a full analysis product).
- **Why:** ROADMAP's Phase 10 success criterion #2 literally requires club insights "grounded in real Position Needs... aggregates," but Phase 10's own `Depends on: Phase 6, Phase 9` list does NOT include Phase 11 — and Phase 11 comes after Phase 10 in the roadmap anyway. Blocking Phase 10 on Phase 11, or building Phase 11's full user-facing feature early (scope creep, and pre-empting Phase 11's own design decisions like the exact strong/weak/at-risk thresholds), are both worse than computing the specific numbers this phase's prompts actually need, scoped narrowly to what AI-04 requires.

### Report generation follows Phase 9's provider-agnostic pattern, with its own interface
- **Decision:** A new `ReportGenerator` abstract interface (parallel to Phase 9's `NLQueryParser`, same architectural shape: one method, e.g. `generate(grounding: dict, report_type: str) -> GeneratedReport`), with `get_report_generator()` factory dispatching on the same `LLM_PROVIDER` setting Phase 9 already added. The concrete Anthropic implementation uses a separate, independently configurable model setting — `ANTHROPIC_REPORT_MODEL` (default: a stronger/more capable tier than Phase 9's cheap extraction model) — since narrative report quality benefits more from a stronger model than simple structured-filter extraction did, and reports are requested on-demand (low volume) rather than per-search (higher volume), so the cost trade-off favors quality here.
- **Why:** AI-05 already established "provider-agnostic interface" as this project's LLM integration pattern — Phase 10 is a second, different LLM task (generation vs. extraction) and should follow the same proven shape rather than inventing a new one. A separate model setting (not reusing `ANTHROPIC_MODEL`) avoids forcing one model choice to serve two different quality/cost trade-offs.

### Grounding enforcement: numbers are validated after generation, not just prompted-for
- **Decision:** Every number the LLM is allowed to reference is pre-computed server-side into a single structured "grounding context" dict (the `get_summary()` scores/breakdown for a player report; squad depth/age/contract aggregates + `ClubDetailSerializer`'s existing `transfer_aggregates` for a club-insights report) — this dict is the ONLY source of truth passed into the prompt. After generation, a post-generation validator extracts numeric tokens from the LLM's narrative output and cross-checks each one appears (within reasonable formatting/rounding tolerance) in the grounding dict; the report is rejected/regenerated (once) if it contains a number that doesn't trace back to grounding data, rather than being returned as-is.
- **Why:** Success criterion #3 ("No report ever contains an LLM-invented number") is a hard product guarantee, not a soft preference — a prompt instruction alone ("only use these numbers") is well-known to not fully prevent LLM hallucination. A programmatic post-generation check is the only way to actually guarantee this, consistent with this project's established "never fabricate, verify against ground truth" pattern used throughout every prior phase's own verification process.

### Endpoint shape: always regenerate, no persistence/caching
- **Decision:** `POST /api/players/{id}/scouting-report/` (body: `{"club_id": "..."}`, since tactical/financial fit are club-relative) and `POST /api/clubs/{id}/insights/`. Both return structured JSON: narrative text broken into the named sections ROADMAP specifies (strengths/weaknesses/tactical fit/financial fit/best use case for players; recruitment gaps/over-aged positions/financial constraints for clubs) plus the exact grounding data dict used, for transparency/traceability. Reports are generated fresh on every request — never cached or persisted to the database.
- **Why:** REQUIREMENTS.md's own v2 backlog (`REL-01`: "Report caching/regeneration with data-version-aware invalidation — ship 'always regenerate' first") already establishes this project's explicit stance: ship the simple always-regenerate version now, defer caching to a later release once real usage patterns are known. Echoing the grounding data back in the response directly satisfies "every number... traceable" in a way a caller/tester can verify without cross-referencing a separate endpoint.

### No narrative fallback on generation failure — clean error, never a fabricated report
- **Decision:** If the LLM call fails (timeout, API error, or the post-generation grounding check fails twice), the endpoint returns a clean error response (e.g. `503` with a clear message) — never a template-only or partially-fabricated report. This differs deliberately from Phase 9's 3-tier degradation (a search without AI is still a useful unfiltered list; a "scouting report" synthesized without AI and without real grounding is not a lesser version of the feature, it's a fabrication).
- **Why:** Phase 9's graceful-degradation pattern doesn't transfer here — there is no non-LLM equivalent of a written scouting report the way "show everything, unfiltered" is a reasonable non-LLM equivalent of a search. Returning a fake or fallback-template report would directly violate this phase's core promise (no invented content) in a worse way than just failing cleanly.

### Claude's Discretion
- Exact prompt wording and section ordering within each report type.
- Exact numeric-tolerance rules for the grounding validator (e.g. rounding "€2.3M" from a raw `2340000` figure should pass; a number with no match anywhere in grounding data should fail).
- Whether the validator retries generation once on failure or fails immediately — retry-once is the natural default (transient LLM inconsistency is common; a single retry is cheap for a low-volume, on-demand endpoint) but exact retry/backoff tuning is left open.
- Whether `RecentActivity` gets a new `activity_type` for report requests — not required by AI-03/AI-04's literal wording, and Phase 8 deliberately kept `RecentActivity`'s type list minimal; the planner may add one if low-cost, but it is not a locked requirement.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `get_summary()` — directly reusable, already returns everything a scouting report needs in one call (RMM/CS/TFM/Transfer Probability + breakdowns).
- `ClubDetailSerializer.get_transfer_aggregates` — directly reusable for the transfer-behaviour half of club insights.
- Phase 9's `NLQueryParser`/factory/safety-net pattern — the architectural template this phase's `ReportGenerator` follows, not a new pattern.

### Established Patterns
- No caching/persistence layer exists for any generated content anywhere in this codebase — "always regenerate" is consistent with the project's existing minimal-infra bias (see Phase 6/8's "don't add infra without a forcing reason").
- `django-environ` (`env()`) — the project's config pattern; `ANTHROPIC_REPORT_MODEL` should follow it exactly, matching `ANTHROPIC_MODEL`'s existing style.

### Integration Points
- Downstream: Phase 11's Position Needs analysis may formalize/reuse this phase's lightweight position-needs aggregation logic into its own dedicated, user-facing feature.
- Upstream: depends on Phase 6 (fast scoring, so `get_summary()` stays sub-second) and Phase 9 (the provider-agnostic LLM pattern this phase extends).
