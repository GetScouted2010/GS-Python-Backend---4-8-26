# Master Curation Map

Phase 3 Success Criterion 4: a single document showing, per score, which authoritative
functions/columns from `pixel-perfect-clone-60729/docs/impact_model_v4.1.py` feed it, the
duplicate-function decisions that determined "authoritative," every fix applied during
characterization, and the forks left open for Phase 4's actual port.

This document is the master index over the phase's other deliverables:

- **The oracle snapshot** — `scoring/oracle/scoring_oracle_v1_<date>.csv` + `scoring/oracle/MANIFEST.md`
  (Plan 07 Task 1): one row per real player (~41,708) with `rmm`, `cs`, `tfm`,
  `transfer_probability`, generated by running the calculators documented below over the full
  reconstructed population.
- **The TFM artifact** — `scoring/ml_artifacts/tfm_value_model_v1.joblib` + its `.metrics.json`
  sidecar (Plan 06): the versioned, joblib-dumped `RandomForestRegressor` Pipeline.
- **The characterization modules** — `scoring/characterization/{impact,role_fit,deterministic_scores,tfm_model}.py`
  (Plans 04-06): the actual ported code this map documents.

## RMM (Player Impact)

**Score column in the oracle:** `rmm`. **Port:** `scoring/characterization/impact.py`.

**Authoritative functions (single-definition in the source — not part of the 20-name duplicate
catalogue):**

| Function | Source line | Role |
|---|---|---|
| `_build_std_lookup` | ~1392 | Per-position-group percentile lookup table over `metrics_needed` |
| `_calc_gk_impact_raw` | ~1413 | GK position model (shot-stopping/command/distribution/buildup) |
| `_calc_cb_impact_raw` | ~1473 | CB position model |
| `_calc_fb_impact_raw` | ~1539 | LB/RB position model |
| `_calc_cmf_impact_raw` | ~1616 | CM position model |
| `_calc_dmf_impact_raw` | ~1694 | DMF position model |
| `_calc_amf_impact_raw` | ~1773 | AMF position model |
| `_calc_winger_impact_raw` | ~1851 | LW/RW position model |
| `_calc_cf_impact_raw` | ~1928 | CF position model |
| `add_player_impact` | ~2725 | Orchestrator: normalises position, builds `std_lookup`, dispatches to the 8 position calculators, assembles `"Player Impact"` via `_position_percentile` per position group |
| `_position_percentile` | ~1260 | Rank-based percentile helper `add_player_impact` and `_build_std_lookup` both call |

**Input columns read:** the ~99 renamed stat columns (`docs/FIELD_MAPPING.md`), `Main_Position`/`Position`,
`Minutes`/`Minutes played` (via `_ensure_minutes`'s fallback chain).

**Whole-dataset dependency:** **YES** — `_build_std_lookup` computes position-relative percentiles
via `df.groupby(position_col)`, so RMM for any one player depends on every other player in the same
position group being present in the same call. This is why `generate_scoring_oracle` runs
`compute_rmm_column` once over the full reconstructed population, not per-player.

**Where the port lives:** `scoring/characterization/impact.py`. Oracle entry point:
`compute_rmm_column(players_df) -> pd.Series` (indexed by `player_id`).

**Cross-score data flow:** RMM (`"Player Impact"`, output as `player_impact` after the
`compute_rmm_column` wrapper) is **required** input to Performance Score
(`deterministic_scores.performance_score`, 20% weight inside Transfer Probability) and is one of
the 4 cross-plan features (`player_impact`) `tfm_model.build_transfer_value_dataset` /
`build_oracle_player_features` read off `players_df`. Both `generate_scoring_oracle.py` and
`train_tfm_model.py` explicitly merge `players_df["player_impact"] = players_df["player_id"].map(rmm)`
**before** calling anything downstream — without this merge, Performance Score and the TFM
features silently read NaN across the whole population (03-07-PLAN.md's central wiring concern).

## Compatibility Score

**Score column in the oracle:** `cs`. **Port:** `scoring/characterization/role_fit.py` +
`deterministic_scores.py`.

**Authoritative functions:**

| Function | Source line | Role |
|---|---|---|
| `calculate_subjective_role_fit_for_player_to_team` | 2446 | Role Fit Score: player's role vector vs. the target club's style-demand vector (`weighted_overlap_score`) |
| `"Compatibility Score" assembly` | 3798-3802 | `_avg_non_null([clip(role_fit_score), clip(similarity_pct), bonus])` — ported as `role_fit.compatibility_score` |
| `get_role_scores_from_dataset` / `extract_playing_style_from_dataset` | def@1055/def@3133/def@3120 (identical duplicates — see DUPLICATE_FUNCTIONS.md) | Recovers the player's own best-fitting role, needed for the "matches club's best-fit role" bonus term and the `role_pct` cross-plan feature; ported narrowly as `role_fit.get_player_own_best_role` |

**Whole-dataset dependency:** **YES**, via club context — `calculate_subjective_role_fit_for_player_to_team`

`compute_cs_tp_for_pairs` (below) needs `role_scores_wide` (all players' role scores) to look up
each player's role vector. Not population-relative like RMM's percentiles, but not a pure
row-local computation either.

**Where the port lives:** `scoring/characterization/role_fit.py` (role-fit + bonus term) +
`scoring/characterization/deterministic_scores.py`'s `compute_cs_tp_for_pairs` (the per-player-vs-club
orchestrator — **new, not in source**; see "Cross-plan wiring contracts" below).

**Cross-score data flow:** `compatibility_score`/`role_pct` (from the same `compute_cs_tp_for_pairs`
call) are 2 of the 4 cross-plan features `tfm_model.build_transfer_value_dataset` /
`build_oracle_player_features` read off `players_df` — merged on by both `train_tfm_model.py` and
`generate_scoring_oracle.py` before those functions run.

## Financial Fit (TFM)

**Score column in the oracle:** `tfm`. **Port:** `scoring/characterization/tfm_model.py`.

**Authoritative functions:**

| Function | Source line | Role |
|---|---|---|
| `build_transfer_value_dataset` | **4935** (kept — 4887 is a truncated/orphaned duplicate with no `return`, see DUPLICATE_FUNCTIONS.md) | Builds the 33-nominal-feature training dataset from matched historical transfer events |
| `train_transfer_value_model` | 5569 | Fits the `RandomForestRegressor` Pipeline, returns metrics |
| `RandomForestRegressor(...)` | ~5638-5652 | `n_estimators=300, max_depth=12, min_samples_leaf=3, random_state=42, n_jobs=-1` — **the sklearn artifact itself** |
| `add_value_labels` | 5676 | `fee_diff`/`fee_ratio_actual_to_pred`/`value_verdict` post-prediction labeling (not used by the oracle, ported for completeness) |
| `parse_money_to_numeric` | **13668** (kept over 4738 — last-wins) | Fee/market-value string → float |
| `safe_div` | **13699** (kept over 4762 — last-wins) | Div-by-zero-safe ratio, feeds `mv_to_fee_ratio` |
| `season_to_year` | **13705** (kept over 4783 — last-wins) | `"2022-2023"` → `2022` |
| `contract_to_years_left` | **13716** (kept over 4793 — last-wins) | Contract-expiry → years-left, feeds `contract_years_left` |

**Input columns read:** `transfers_df` (`Player`, `Year`, `Position`, `Age`, `Fee`, `Dealing_Club`,
`Club`, `League`, `is_loan`) joined to `players_df` by `Player`+mapped-season, plus (per the
cross-plan precondition below) `player_impact`/`compatibility_score`/`performance_score`/`role_pct`
if present.

**Whole-dataset dependency:** **YES** — every club-aggregate feature (`club_avg_in_fee`,
`seller_hist_avg_out_fee`, `club_pos_avg_in_fee`, etc.) is a `groupby("Club"/"Dealing_Club")` over
the FULL `transfers_df`, so a single player's TFM feature row depends on every other transfer in
the dataset.

**Where the port lives:** `scoring/characterization/tfm_model.py`. Oracle entry point (new, not in
source): `build_oracle_player_features(players_df, transfers_df)` — builds one feature row **per
player** (not per matched historical transfer event) using the player's current club as both
buying- and selling-club context, since a real player isn't actually mid-transfer; see the
function's docstring for the full rationale. `generate_scoring_oracle.py` then calls
`pipeline.predict()` on the resulting feature matrix.

**Cross-plan wiring contract (critical):** in the original monolithic script, `player_impact`,
`performance_score`, `compatibility_score`, and `role_pct` are already columns on `players_df` by
the time `build_transfer_value_dataset` runs (they were computed earlier in the same script).
This project splits that into separate Plan 04/05/06/07 modules, so **the caller is responsible
for merging those 4 columns onto `players_df` before calling `build_transfer_value_dataset` /
`build_oracle_player_features`** — `tfm_model.py` itself never computes them, only reads them if
present (`_OPTIONAL_PLAYER_COLUMNS`, mirroring the source's own
`[c for c in feature_cols if c in model_df.columns]` silent-exclusion pattern). Both
`train_tfm_model.py` (Plan 06) and `generate_scoring_oracle.py` (Plan 07) perform this merge
explicitly, in the same order: RMM first, then Compatibility/Performance/role_pct, then the TFM
feature build.

## Transfer Probability

**Score column in the oracle:** `transfer_probability`. **Port:**
`scoring/characterization/deterministic_scores.py`.

**Authoritative functions:**

| Function | Source line | Role |
|---|---|---|
| `"Transfer Probability %"` (tp) formula | **3809-3814** | `tp = (0.30*compat/100 + 0.20*perf/100 + 0.20*financial/100 + 0.30*contract_fit) * 100`, then `round(tp, 1)` at line 3840 |
| `"Financial Score"` assembly | 3804-3807 | `_avg_non_null([_fit_to_score(age_fit), _fit_to_score(mv_fit)])` |
| `"Performance Score"` assembly | 3790-3796 | `_avg_non_null([clip(player_impact), clip(perf_team_pct), clip(perf_target_pct), clip(perf_own_pct), clip(50+2*impact_delta)])` |
| contract-expiry banding | 3734-3741 | `1.0` if `yrs<=1`, `0.7` if `yrs==2`, `0.4` if `yrs==3`, else `0.1`; `0.5` on unparseable |
| `classify_fit` | 1029-1037 | Generic tolerance-banded fit classifier (feeds Financial Score's mv_fit) |
| `classify_age_fit` | **2698** (kept over 1325 — last-wins; the 2698 copy is the one in effect at the shortlist scoring block per module execution order) | Age-fit classifier (feeds Financial Score's age_fit) |

**Input columns read:** `player_impact` (RMM, required, Plan 04), `compatibility_score`/`role_pct`
(Plan 05's own output), the target club's current squad (`Age`/`Market value`, for the Financial
Score baseline), `Contract expires`.

**Whole-dataset dependency:** **NO** — row-local given its inputs. The formula itself only needs
one player's `compatibility_score`/`performance_score`/`financial_score`/`contract_fit` values; it
is the *inputs* (Compatibility Score, Performance Score) that carry whole-dataset dependencies, not
this formula itself.

**Where the port lives:** `scoring/characterization/deterministic_scores.py`'s
`compute_cs_tp_for_pairs` — **new, not in source** — is this project's cross-plan wiring contract:
the per-player-vs-club-context orchestrator that computes Compatibility Score, Financial Score,
Performance Score, `contract_fit`, `role_pct`, and Transfer Probability together in one pass and
returns a DataFrame indexed by `player_id`. Both `train_tfm_model.py`'s feature build and
`generate_scoring_oracle.py`'s oracle snapshot call it once, with `club_context=None` (each player
evaluated against their own current club).

**Cross-score data flow:** `player_impact` (RMM) feeds Performance Score (20% of Transfer
Probability); `compatibility_score`/`performance_score`/`role_pct` are 3 of the 4 features TFM's
`build_transfer_value_dataset`/`build_oracle_player_features` read off `players_df`. This means
Transfer Probability and TFM share upstream inputs (RMM, Compatibility Score) but are otherwise
fully independent scores computed by different mechanisms (deterministic formula vs. sklearn
regression) — see the resolved mapping below.

## Resolved escalations

### TFM / Transfer Probability mapping resolution (LOCKED, 03-CONTEXT.md, resolved 2026-07-21)

> **Research finding:** direct inspection of `impact_model_v4.1.py` confirmed the
> `RandomForestRegressor` (lines 5638-5652) predicts `log_fee` (transfer fee/value) — **NOT** a
> probability. The column literally named `"Transfer Probability %"` (lines 3809-3814) is a
> separate, fully deterministic, non-ML weighted formula
> (`0.30*compatibility + 0.20*performance + 0.20*financial + 0.30*contract_fit`).
>
> **Resolution (locked):** the `RandomForestRegressor` artifact is the **Financial Fit (TFM)**
> artifact, **NOT** Transfer Probability. Train it, joblib-version it, and record its MAE/R² as
> TFM's characterization data. **Transfer Probability is the deterministic weighted-formula
> port** — no ML training, no joblib artifact needed for it; just faithfully port the arithmetic
> and its inputs.

**Rationale (one line):** the source names the ML output `log_fee`/`predicted_fee` — a monetary
value, matching "Financial Fit" — while the deterministic formula is what the source itself labels
`"Transfer Probability %"`; conflating the two (as an earlier, pre-research hypothesis had) would
have wired the wrong artifact into every downstream Transfer-Probability consumer. Confirmed by
Plan 06's `tfm_model.py` (RandomForestRegressor, trained/joblib-versioned) and Plan 05's
`deterministic_scores.py` (`transfer_probability`, zero sklearn imports — grep-verifiable, no
`import sklearn` anywhere in that file).

## Fixes applied

Every non-empty `APPLIED_FIXES` list from the 4 characterization modules, aggregated (the
"no silent fixes" audit trail per 03-CONTEXT.md's fix-threshold policy — only MISSING/ABSENT data
silently defaulted in a way that mathematically distorts a score qualifies; everything else,
however odd-looking, is preserved verbatim):

| Module | Column/Function | Source behavior | What changed | Why |
|---|---|---|---|---|
| `impact.py` | `Minutes` (`_ensure_minutes`) | `impact_model_v4.1.py`'s `_ensure_minutes` (line ~1249): if no Minutes-equivalent column exists at all, silently sets the whole `"Minutes"` column to `0` for every row — every `_calc_*_impact_raw` then multiplies by `_minutes_factor(0) == 0.55`, a fabricated reliability penalty applied population-wide. | Raises `ValueError` instead of defaulting the whole column to 0 when no Minutes-equivalent column exists. Per-row NaN Minutes (column present, individual player unknown) are left as NaN and flow through `_safe_num`'s NaN→0.0 coercion exactly as upstream — that per-player quirk is unchanged. | A missing Minutes-equivalent column is a reconstruction bug (the ORM→DataFrame bridge failed), not a legitimate "nobody played" population state — it should fail loudly, not silently distort every player's RMM by the same fabricated floor. |
| `role_fit.py` | `calculate_subjective_role_fit_for_player_to_team` | Source computes `build_team_style_vector()` unconditionally; `normalize_series()` silently zero-fills an all-NaN club style vector (`fillna(0.0)`) — the ~77%-null case (FIELD_MAPPING.md §3) — which deterministically produces Role Fit Score `== 0.0`, a confidently-wrong "zero fit" result. | Added an explicit guard: if the target club's style vector has no non-NaN `STYLE_COLUMNS` values, return the same NaN/blank result dict the source already returns for its other early-exit branches, instead of proceeding to a zero-filled computation. | An unknown club style should produce an honest "we don't know" (NaN), not a confidently-wrong zero score. |
| `role_fit.py` | `get_player_own_best_role` | Source's `get_role_scores_from_dataset`/`extract_playing_style_from_dataset` read `float(row.get(role, 0))`, which only substitutes 0 when the column is entirely ABSENT — not when the cell value is NaN (a wide-pivoted column present-but-NaN for an unscored role). A stray NaN reaching `max(scores, key=scores.get)` produces undefined ordering. | Explicitly coerces NaN role-score cells to "not a candidate" (excluded, not zero-filled) before taking the max; returns `(None, np.nan, {})`, not `(None, 0, {})`, when no role has a real value. | Consistent with this project's no-silent-zero-fill rule; an undefined `max()` result over NaN-containing scores is itself a latent bug, independent of the zero-fill question. |
| `deterministic_scores.py` | `compute_cs_tp_for_pairs`'s Financial Score baseline (`avg_age`/`avg_mv`) | Source computes the age/market-value baseline from a club's **transfer-arrival history** (`club_transfer_profile`, needs `transfers_df`). | `compute_cs_tp_for_pairs`'s signature (03-05-PLAN.md) doesn't take `transfers_df`, so this port baselines age/MV fit against the target club's **current squad** (from `players_df`) instead. `financial_score()` itself — the pure 2-term average — is unchanged. | Documented adaptation to this project's function-signature split, not a silent substitution; the underlying "compare this player to what the club already has" intent is preserved, just sourced from current roster instead of historical arrivals. |
| `tfm_model.py` | `build_transfer_value_dataset`'s optional-player-column handling (`_OPTIONAL_PLAYER_COLUMNS`) | Source reads `player_impact`/`compatibility_score`/`performance_score`/`role_pct` under their raw human-readable literal names (`"Player Impact"`, etc.) because that's how they were named on the source's own in-memory `players_df`. | `_OPTIONAL_PLAYER_COLUMNS` accepts EITHER the source-literal name or this project's actual lowercase snake_case name (Plan 04/05's locked naming convention) for each optional column. | Naming adaptation to this project's real reconstructed column names, not a value-distorting fix — `SimpleImputer` still performs all genuine missing-value handling; a genuinely absent column is still silently excluded from `feature_cols` exactly as the source's own filter does. |
| `tfm_model.py` | `build_transfer_value_dataset`'s `"Contract"` column mapping | Source's optional `"Contract"` raw-text column (feeds `contract_to_years_left`'s year-regex extraction) doesn't exist under that name on this project's reconstructed `players_df`. | `_OPTIONAL_PLAYER_COLUMNS` maps `"Contract expires"` (this project's actual date field) to the same `contract_raw` target; `str(<the date>)` still contains a 4-digit year the unmodified regex extracts correctly. | `contract_to_years_left` itself is unchanged — this is a column-name adaptation only. |

## Open forks for Phase 4 (documented, NOT resolved here)

Per 03-RESEARCH.md's "Related, Lower-Stakes Ambiguities" (Open Questions 2 & 3) — these are real
forks in the source with more than one plausible reading; this phase deliberately picks one
interpretation for the oracle and documents the other rather than silently discarding it:

1. **The Compatibility Score source fork** — the codebase has TWO distinct notions of
   "compatibility": (a) the legacy `PlayerClubCompatibility.score` values imported wholesale from
   `Compatability Scores/*.csv` in Phase 1 (a static, pre-computed per-player-per-club score,
   8.19M rows), and (b) the fresh `calculate_subjective_role_fit_for_player_to_team` +
   `compatibility_score()` script computation this phase ports and the oracle uses. **The oracle
   uses (b), the fresh script computation** — it's the score `impact_model_v4.1.py` actually
   computes at runtime, matching this phase's "characterize the script, not the imported static
   data" scope. Phase 4 must decide which of the two the production port ultimately serves through
   the API; this phase does not make that call.
2. **The RMM primitive choice** — `impact_model_v4.1.py` has two related-but-distinct player-value
   primitives: `add_player_impact`'s context-free, population-relative `"Player Impact"` (this
   phase's RMM, per 03-RESEARCH.md's "least-ambiguous" recommendation), and `"Performance Score"`'s
   club-contextual blend (which itself takes Player Impact as one of five terms). **The oracle's
   `rmm` column is Player Impact**, not Performance Score. Phase 4 should confirm this matches the
   PRD's intended "Player Score/RMM" semantics before treating it as final.
